## What this is

Lesson 13 formalized *what the agent is doing* (the task FSM). This lesson formalizes *what the agent is never allowed to do*: a set of **invariants** - architecture already accepted, technical decisions already settled, stack limits, and business rules - that no request in any conversation may talk the agent out of. Everything else from lesson 13 - the task FSM, the personalization profile, short-term/long-term memory - is unchanged.

### Invariants are their own memory layer

```rust
enum InvariantCategory { Architecture, TechDecision, StackConstraint, BusinessRule }

struct Invariant {
    id: String,
    category: InvariantCategory,
    statement: String,
    rationale: String,
    forbidden_terms: Vec<String>,   // optional - see "two layers of enforcement" below
}

struct InvariantSet {
    invariants: Vec<Invariant>,
}
```

`InvariantSet` is persisted to its own file (`invariants.json`, separate from the profile, the task FSM, and both memory layers) and is never touched by an LLM extractor. Just like the task FSM's stage in lesson 13, an invariant only ever changes through an explicit API call - `POST /api/invariants` to add one, `POST /api/invariants/remove` to take one away. Nothing in a chat message can add, remove, or edit an invariant, no matter how it's phrased.

On first run, with no `invariants.json` on disk yet, the agent seeds itself with **this repo's own real, already-decided constraints** - straight out of [`AGENTS.md`](../AGENTS.md) and [`DEPLOYMENT.md`](../DEPLOYMENT.md): no Docker on the VDS, deploys run as user-level systemd units (never root), no shared Cargo workspace across lessons, `static/index.html` is always compiled in via `include_str!`, state transitions are never LLM-inferred, and lesson 04's deploy stays deliberately broken. Dogfooding the project's own decisions means the demo is concrete and checkable against the actual docs, not a list of made-up rules.

### Two layers of enforcement

An invariant can optionally carry `forbidden_terms`: short phrases that, if they appear anywhere in the user's raw message (case-insensitive), block the turn **before the model is ever called**. This check runs in plain Rust inside `Agent::find_violated_invariant` - no network round-trip, no dependence on the model's mood that day, no token spent. The refusal text itself is assembled by `format_invariant_refusal`, not generated by the LLM, so it's guaranteed to name the right invariant and never drifts or gets talked around.

That's deliberately narrow, though - a fixed keyword list can't catch every way a request might conflict with a business rule phrased in prose. So **every** invariant, whether or not it has forbidden terms, also rides along in `format_invariants_block`: a system message injected into *every single request*, instructing the model to check the request against the full list before answering, and - if something conflicts - to refuse, name the specific invariant (id, category, and why it exists), and offer a compliant alternative when one exists. This is the "явно учитывал их в рассуждениях" part: the model isn't just told the invariants exist, it's told to check them first, on every turn, and to show its refusal in those terms.

`build_context` (extended again from lesson 13) puts the invariants block **first**, ahead of even the personalization profile - the most stable layer there is, since nothing said in a single conversation is allowed to move it, and everything else (profile, long-term facts, the task FSM, live dialogue) is subordinate to it.

### What happens at a conflict

1. A message trips a `forbidden_terms` match (e.g. asking to "add a Dockerfile"): the turn never reaches the network. `Agent::respond` returns the canned refusal immediately, `MemoryReport.blocked_by_invariant` is set to the invariant's id, and `MemoryReport.actual` (real API usage) is `None` since no call was made. The turn still lands in short-term history - both the user's ask and the refusal - so the conversation reads naturally and the same guardrail applies again if the user repeats the request.
2. A message conflicts with an invariant *semantically*, without any forbidden term (e.g. "let's just skip the review step before merging" against a business rule about validation): the hard pre-check finds nothing, the request goes to the model as normal, and the model is expected to catch the conflict itself from `format_invariants_block` and refuse in the same terms - id, category, why. This path depends on the model actually following the instruction; the hard path doesn't.

Either way, the invariant that blocks a request is never silently worked around - refusing and explaining is the only sanctioned response `format_invariants_block` allows for a genuine conflict.

### Explaining the refusal

Both paths produce the same shape of explanation: which invariant (`id` and `category`), what it says, why it exists, and - for the deterministic path - an explicit note that this can't be argued around in chat; changing it requires an explicit `/api/invariants/remove` call, not a persuasive request. That symmetry is intentional: whether Rust or the model wrote the refusal, the reasoning it shows the user is the same.

### Token cost

`invariants_tokens` in `MemoryReport` covers the whole invariants block the same way `profile_tokens` and `working_memory_tokens` already covered their own layers - visible per-request in the UI's token line, right next to the count that shows whether the last turn was blocked.

## Run

```bash
OPENAI_API_KEY=sk-... cargo run
```

Then open http://localhost:3000. The seeded invariants ("no-docker", "user-level-systemd", etc.) are visible immediately in the Invariants panel - try asking the chat to "just add a Dockerfile for this" and watch it refuse before any request reaches the model.

Or drive it directly via curl:

```bash
# List the (seeded) invariants
curl localhost:3000/api/invariants

# Add one with a hard, deterministic block
curl -X POST localhost:3000/api/invariants \
  -H 'Content-Type: application/json' \
  -d '{"id": "no-python", "category": "stack_constraint", "statement": "Lessons are written in Rust, not Python.", "rationale": "Consistency with every other lesson.", "forbidden_terms": ["rewrite it in python", "switch to python"]}'

# This gets refused deterministically, without ever calling the model
curl -X POST localhost:3000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"message": "Can we just rewrite it in Python, it would be faster to prototype?"}'

# Remove an invariant explicitly - the only way its rule stops applying
curl -X POST localhost:3000/api/invariants/remove -H 'Content-Type: application/json' -d '{"id": "no-python"}'

curl localhost:3000/api/memory   # full inspection, including invariants and blocked_by_invariant
```

| `LONG_TERM_FILE` | no | `long_term.json` |
| `INVARIANTS_FILE` | no | `invariants.json` |
| `CONTEXT_LIMIT_TOKENS` | no | `64000` |
| `PRICE_PER_1M_INPUT_TOKENS` | no | unset (cost hidden) |
| `PRICE_PER_1M_OUTPUT_TOKENS` | no | unset (cost hidden) |
| `PORT` | no | `3000` |

`INVARIANTS_FILE` persists the full invariant set. Delete it (or point `INVARIANTS_FILE` at a fresh path) to get a clean re-seed of this repo's own default invariants on the next start.
