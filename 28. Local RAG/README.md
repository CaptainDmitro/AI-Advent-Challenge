## What this is

[Lesson 22](../22.%20First%20RAG%20Query)'s RAG pipeline, with the answer
generated by [lesson 26](../26.%20Local%20LLM)'s local model instead of a
hosted API. Next to it, the same prompt goes to a cloud model, so the two can
be compared on lesson 22's 10 control questions.

```
 on this machine (or on the VDS + the Mac's Ollama through the tunnel)
 ─────────────────────────────────────────────────────────────────────
 question ─▶ embed ─▶ index (lessons 21/22, in memory) ─▶ top-k chunks
                                                              │
                                   prompt: [n] file — section … Question: …
                                                              │
                                  ┌───────────────────────────┴──────────────┐
                                  ▼                                          ▼
                     Ollama: qwen2.5:3b (local)              cloud model (optional)
                                  ▼                                          ▼
                               answer                                     answer
```

- **Index from week 6, unchanged.** [`src/index.rs`](./src/index.rs) is lesson
  22's copy of lesson 21's index: the same 27 files compiled into the binary,
  the same structural chunks (one per Markdown section or top-level Rust item,
  joined under 300 characters, split over 1800), the same local hashed TF-IDF
  embedder. The index is built in memory at start-up in milliseconds.
- **Local retrieval.** The question is embedded in-process and the `k`
  closest chunks (5 by default) are found by cosine similarity. No network.
  `EMBEDDER=ollama` swaps in neural embeddings from the same local Ollama
  (`nomic-embed-text` through its `/v1/embeddings`), which also stays on the
  machine.
- **Local generation.** The chunks and the question are merged into lesson
  22's RAG prompt word for word: numbered fragments `[n] file — section`,
  "answer only from the fragments, cite them as `[n]`", then the question.
  The prompt goes to Ollama's native `/api/chat` with `stream: false`.
  `num_ctx` is set to 8192, because five chunks and the rules come to 2–3k
  tokens, and Ollama's default window would silently cut the start of the
  prompt.
- **Cloud for comparison, optional.** With `OPENAI_API_KEY` set, the same
  messages go to an OpenAI-compatible `/chat/completions` (DeepSeek by
  default) at the same temperature. Retrieval runs once per question, so both
  models get the same prompt, byte for byte. Without the key the cloud side is
  off and nothing leaves the machine: the page shows **cloud: off (fully
  local)**.

### How the comparison is measured

Every control question records what a correct answer says and which section
it comes from. They are lesson 22's ten, so the numbers are comparable with
lesson 22. Each question can be asked **1–5 times per model** (`runs`), at a
chosen temperature. Each model's runs go one after another, so the local
model's speed isn't split between parallel requests. The two models run side
by side.

| | What is measured | How |
|---|---|---|
| **Quality** | expected facts stated | each fact passes if the answer contains any of its variants, ignoring case (lesson 22's checks) |
| | cites the expected source | the answer cites `[n]`, and fragment `n` is from the expected file |
| **Speed** | time per answer | wall-clock time of the call, as the server sees it |
| | completion tokens per wall-clock second | the same yardstick for both: network and prompt processing included |
| | generation tok/s, prefill, load | local only, from Ollama's own nanosecond counters: generation speed, time to read the 2–3k-token prompt, and model load time |
| **Stability** | failed calls | errors per run (Ollama down, model not pulled, an API error) |
| | one answer across runs | distinct answer texts over the runs, whitespace ignored. 1 means the same answer every time |
| | fact score changed between runs | the same question scored differently on another run |
| | answers without any `[n]` | whether the model keeps to the output format at all |

The page has a free-form question box and the table of control questions.
**Run all 10** fills the table row by row: facts, citation, time and the
number of distinct answers, per model. Below it is a summary of quality,
speed and stability for local vs cloud. Clicking a row shows both answers
side by side with the facts marked ✓/✗, every extra run, the retrieved chunks
(the expected ones outlined) and the exact prompt. The local model can be
switched to any other pulled model from the picker.

The same comparison runs from the terminal and prints the tables and every
answer:

```bash
cargo run -- eval --runs 3
```

`--only local` skips the cloud, `--temperature 0.7` and `--k 3` change the
settings.

### Results

Measured on the deployed app (`http://<VDS host>:4028`). Retrieval and the
cloud calls ran on the VDS. Generation ran on an M-series MacBook (16 GB)
through the tunnel: `qwen2.5:3b` (Q4_K_M) on Ollama 0.40.3, against
`deepseek-v4-flash`. All 10 control questions, top-5 chunks, 3 runs per
question per model, at temperature 0 and at 0.7. Retrieval found the
expected source for 10/10 questions in under 1 ms, and both models got the
same ≈1.46k-token prompt.

| | | local `qwen2.5:3b`<br>t = 0 | cloud `deepseek-v4-flash`<br>t = 0 | local<br>t = 0.7 | cloud<br>t = 0.7 |
|---|---|---|---|---|---|
| **Quality** | expected facts stated | **83%** | **97%** | 82% | 98% |
| | answers citing the expected source `[n]` | **0/30** | **30/30** | 0/30 | 30/30 |
| | answers in the question's language (English) | 30/30 | **20/30** | 30/30 | 20/30 |
| **Speed** | time per answer | 3.2 s | 2.1 s | 2.3 s | 1.9 s |
| | answer length, tokens | 83 | 268 | 80 | 232 |
| | completion tokens / wall-clock second | 31 | 123 | 36 | 115 |
| | Ollama: generation · prefill · load | 43 tok/s · 1.1 s · 0.08 s | – | 44 tok/s · 0.3 s · 0.01 s | – |
| **Stability** | failed calls | 0/30 | 0/30 | 0/30 | 0/30 |
| | questions with one answer across 3 runs | **6/10** | **0/10** | 1/10 | 0/10 |
| | questions whose fact score changed between runs | **0/10** | 1/10 | 3/10 | 0/10 |

Per question (facts found in each of the 3 runs, at t = 0):

| # | local | cloud | | # | local | cloud |
|---|---|---|---|---|---|---|
| q01 | 2 2 2 / 2 | 2 2 2 / 2 | | q06 | 1 1 1 / 2 | 2 2 2 / 2 |
| q02 | 3 3 3 / 3 | 3 3 3 / 3 | | q07 | 4 4 4 / 4 | 4 4 3 / 4 |
| q03 | 1 1 1 / 1 | 1 1 1 / 1 | | q08 | 4 4 4 / 5 | 4 4 4 / 5 |
| q04 | 2 2 2 / 2 | 2 2 2 / 2 | | q09 | 3 3 3 / 3 | 3 3 3 / 3 |
| q05 | 2 2 2 / 3 | 3 3 3 / 3 | | q10 | 1 1 1 / 3 | 3 3 3 / 3 |

What this shows:

- **Quality: the local model reads the context well but ignores the format.**
  With the same five chunks, the 3B model states 83% of the expected facts,
  against 97% for the cloud model. It loses them mostly by paraphrasing.
  q10 says "a deterministic keyword pre-check" instead of naming
  `forbidden_terms`, and q06 says "non-blocking" without the reason
  (rustfmt). q08 gives only the fixed-window sizes. But it **never** writes
  the `[n]` citations the rules ask for: 0 of 60 answers. The cloud model
  cites every time. The cloud model, though, answers an English question
  in Russian, Ukrainian or Chinese a third of the time, against the "in the
  language of the question" rule. The local model never does.
- **Speed: the cloud is faster per answer, the local model writes less.**
  The local answer takes 2.3–3.2 s: ≈ 0.3–1.1 s to read the 1.46k-token
  prompt, then ≈ 43 tok/s. The model stays loaded, so load time is ~0. The
  cloud model streams 3–4× more tokens per second but writes 3× longer
  answers, so per answer it is only 1.2–1.5× faster. Retrieval is shared by
  both models and takes under 1 ms.
- **Stability: the local model is the more predictable one.** At t = 0 it
  gives the same text on 6 of 10 questions, and the same facts on all 10.
  The cloud model never repeats its text, even at temperature 0, though its
  facts barely move. At t = 0.7 the local model starts to drift: q09 and q10
  swing between 1/3 and 3/3. Neither side failed a single call.

So the fully local pipeline works and needs nothing but the Mac. Its answers
are short and stable: every expected fact on 6 of 10 questions, most of them
on 2 more. What it doesn't give is citations. A pipeline that has to show its
sources (lessons 24–25) would need a larger local model, or the code would
have to attach the sources itself instead of asking the model to.

To reproduce, open the page, set runs to 3, and click **Run all 10** (or run
`cargo run -- eval --runs 3`).

### Verification

`cargo test` needs neither Ollama, nor a cloud key, nor the network. A fake
Ollama and a fake cloud model (axum routers on random ports) know nothing
about the repo. They echo the context back when there is one, so retrieval
and the prompt are what's tested.

- `retrieval_is_local_and_finds_the_expected_source_for_every_control_question`:
  the local embedder finds a chunk of the expected file in the top 5 for all
  10 questions.
- `both_models_get_the_same_prompt_and_are_scored_the_same_way`: for every
  control question, Ollama and the cloud receive identical `messages` (lesson
  22's rules, every chunk under its `[n] file — section`, the question last).
  Ollama gets `stream: false`, temperature 0 and `num_ctx: 8192`. Ollama's
  counters become 40 tok/s generation, 400 ms prefill and 250 ms load. Both
  answers cite the expected source and score ≥ 70% of the facts.
- `repeated_runs_measure_stability`: at temperature 0, three runs give one
  distinct answer. Above 0 the fake varies its answers, which gives three. A
  model that fails every second call gives 2 errors out of 4, with Ollama's
  message. Asking for the cloud with no key says to set `OPENAI_API_KEY`.
- `http_api_compares_and_reports_errors`: `/api/config`, `/api/status`,
  `/api/cases`, `/api/ask` with a control question and 2 runs, a free
  question to the local model only, an empty question, an unknown case, and
  Ollama down (the error is on the local answer, the retrieved chunks are
  still shown).
- `control_questions_are_grounded_in_the_corpus`, `citations_are_parsed`,
  `normalizes_ollama_host_like_ollama_does`, plus the index's own tests.

## Run

Ollama with the model from lesson 26 (macOS):

```bash
brew services start ollama
```

```bash
ollama pull qwen2.5:3b
```

Fully local, with no cloud key. Open http://localhost:3000:

```bash
cargo run
```

With a cloud model to compare against:

```bash
OPENAI_API_KEY=sk-... cargo run
```

With neural embeddings, also from Ollama:

```bash
ollama pull nomic-embed-text
```

```bash
EMBEDDER=ollama cargo run
```

Over HTTP:

```bash
curl -s localhost:3000/api/ask -H 'Content-Type: application/json' \
  -d '{"case_id": "q03", "runs": 3}' | jq '.results[] | {backend, model, stability, answer: .runs[0].text}'
```

| Endpoint | |
|---|---|
| `GET /api/config` | embedder, chunks, local model, `num_ctx`, cloud model (`null` when off) |
| `GET /api/status` | Ollama's version and pulled models, or why it can't be reached |
| `GET /api/cases` | the 10 control questions |
| `POST /api/ask` | `{question \| case_id, k?, runs?, temperature?, backends?, local_model?}` → retrieved `sources`, `messages`, and per model its `runs` and `stability` |

## Configuration

| Variable | Required | Default |
|---|---|---|
| `OLLAMA_HOST` | no | `http://localhost:11434`, with or without `http://` |
| `OLLAMA_MODEL` | no | `qwen2.5:3b` |
| `OLLAMA_NUM_CTX` | no | `8192` |
| `EMBEDDER` | no | `local`: hashed TF-IDF in-process. `ollama`: Ollama's `/v1/embeddings`. `openai`: a remote `/embeddings` (the only one that leaves the machine) |
| `OLLAMA_EMBED_MODEL` | with `ollama` | `nomic-embed-text` |
| `EMBEDDING_API_KEY`, `EMBEDDING_BASE_URL`, `EMBEDDING_MODEL` | with `openai` | as in lesson 22 |
| `OPENAI_API_KEY` | no | unset = no cloud comparison, fully local |
| `OPENAI_BASE_URL` | no | `https://api.deepseek.com` |
| `OPENAI_MODEL` | no | `deepseek-v4-flash` |
| `PORT` | no | `3000` |

## Deploy

The pipeline deploys it to `http://<VDS host>:4028` on push to `master`, as the
newest web-app lesson (see [`../DEPLOYMENT.md`](../DEPLOYMENT.md)). The
retrieval runs on the VDS inside the binary. The VDS has no GPU and no
Ollama, so generation uses **the Ollama on your Mac** through lesson 26's
reverse SSH tunnel:

```bash
"../26. Local LLM/tunnel.sh" <user>@<vds-host> -i ~/path/to/key
```

The pipeline supplies the `OPENAI_*` secrets, so the deployed page shows the
cloud model next to the local one. While the tunnel is down, the status at
the top turns red and the local answers show "Can't reach Ollama". The cloud
answers and the retrieved chunks keep working. ↻ turns it green once the
tunnel is back.
